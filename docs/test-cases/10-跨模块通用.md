1. 访问 `/dashboard`

|------|-----|
| 模块 | 跨模块通用 |

| 类型 | 功能 |
| 前置条件 | 后端已配置 RateLimiter（具体阈值以部署 config 为准，本用例验证机制存在性） |

**测试步骤**：
1. 用脚本对登录接口 `POST /api/v1/auth/login` 持续高频请求，直至触发限流

### TC-COMM-I-001 POST /auth/login 登录

| 字段 | 值 |
|------|-----|

### TC-COMM-I-009 全局错误响应格式统一

| 字段 | 值 |
|------|-----|
| 模块 | 跨模块通用 |
| 优先级 | P1 |
| 类型 | 接口 |
| 前置条件 | 任意异常路径 |

**测试步骤**：
1. 触发 5 类异常各 1 个：401（不带 token）/ 403（越权访问他人资源）/ 404（访问不存在的 ID）/ 422（参数缺失）/ 500（构造内部错误）
2. 检查每个错误响应的 JSON 结构

**预期结果**：
1. 所有错误响应统一为 `{code: 业务码 int, message: 文案 string, data: null, traceId: uuid string}` 4 字段结构（来源 02-后端详细设计.md §6.3 biz_handler L757-779）
2. HTTP 状态码与业务码定义中的 HTTP 字段一致（如 BIZ_UNAUTHORIZED=2001 对应 HTTP 401，BIZ_FORBIDDEN=2002 对应 403）；`traceId` 字段在所有响应中均不为空，便于日志追踪
