### 问题 4: sessionId 类型转换错误

**时间**: 2026-05-08  
**影响**: AI 对话显示"抱歉，未收到有效回复。"  
**严重程度**: 🟡 P1

#### 现象
```
invalid literal for int() with base 10: 'chat-session-1778284507069'
```

#### 根因分析
后端代码假设 sessionId 一定是数字字符串，直接转换：

```python
# ❌ 错误代码
session_id: int | None = int(req.session_id) if req.session_id else None
```

但前端发送的是：`"chat-session-1778284507069"`（包含非数字字符）

**为什么会出现？**
- 后端没有做防御性编程
- 对外部输入缺乏容错处理
- 没有考虑前端可能发送不同格式的 sessionId

#### 修复方案
✅ 添加 try-except 安全处理类型转换  
✅ 如果转换失败，创建新会话  
✅ 同时修复了 auth_service.py 中的类似问题

### 2. 配置管理规范

#### 2.1 统一配置源

**原则**：所有实际运行的配置必须记录在 `docs/部署文档.md` 的"当前运行环境信息"章节

**必须记录的配置**：
- 数据库连接信息（主机名、端口、用户名、密码）
- Redis 连接信息
- JWT 配置（Secret、有效期）
- 服务端口映射
- 容器名称和网络配置

#### 2.2 配置一致性检查

**规则**：
1. `docker-compose.yml` 必须与部署文档一致
2. `.env.example` 必须与实际配置格式一致（密码可以用占位符）
3. 多个 docker-compose 文件之间的配置必须对齐

**检查方法**：
```bash
# 查看当前运行的配置
docker exec fde-mate-api env | grep -E "DATABASE_URL|REDIS_URL|JWT_SECRET"

# 与部署文档对比
cat docs/部署文档.md | grep -A 10 "API 环境变量"
```

### 3. 前后端 API 契约管理

#### 3.1 字段命名规范

**规则**：
- 后端 Pydantic Schema 使用 `alias` 定义前端字段名
- 前端 TypeScript 接口必须与后端 alias 完全一致
- 使用 `camelCase` 作为前后端通信的字段名格式

**示例**：
```python
# 后端
class ChatRequest(BaseModel):
    assistant_id: str = Field(alias="assistantId")  # alias 是前端字段名
```

```typescript
// 前端
export interface CopilotRequest {
  assistantId: string  // 必须与后端 alias 一致
}
```

#### 3.2 类型转换规范

**后端防御性编程**：
```python
# ✅ 正确：安全的类型转换
try:
    session_id = int(req.session_id)
except (ValueError, TypeError):
    session_id = None

# ❌ 错误：直接转换，可能抛出异常
session_id = int(req.session_id)
```

**前端类型安全**：
```typescript
// ✅ 正确：使用明确的类型
interface CopilotRequest {
  assistantId: string
  sessionId?: string  // 可选字段
}

// ❌ 错误：使用 any
interface CopilotRequest {
  assistantId: any
}
```
